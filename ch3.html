1. Process Concept

What a process is, and how it looks inside memory.

Definition

A process is a program in execution. Its execution must progress in sequential fashion: there is no parallel execution of the instructions of a single process.
  • A program is a passive entity stored on disk (an executable file); a process is active.
  • A program becomes a process when an executable file is loaded into memory.
  • One program can be several processes (e.g. many users running the same program).
Two processes of the same program are still two separate execution sequences: several users running copies of the mail program, or one user opening many web-browser windows. A process may also spawn many processes as it runs.

Current activity

The status of a process’s current activity is represented by the value of the program counter and the contents of the processor’s registers.

Memory layout (4 sections)

  • Text – the executable code
  • Data – global and static variables
  • Heap – memory dynamically allocated at run time
  • Stack – temporary data: function parameters, return address, local variables

Text and data have a fixed size. Only the stack and heap grow and shrink.

Stack and heap behavior

  • Each function call pushes an activation record (parameters, local variables, return address) onto the stack; on return it is popped.
  • The heap grows when memory is dynamically allocated and shrinks when memory is returned to the system.
  • The text and data sizes are fixed; stack and heap change dynamically. The OS must ensure they do not overlap.

2. Process State and PCB

The five states and the record the OS keeps for each process.

The five states

As a process executes, it changes state:
  • New – the process is being created
  • Ready – waiting to be assigned to a processor
  • Running – instructions are being executed
  • Waiting – waiting for some event to occur (e.g. I/O)
  • Terminated – the process has finished execution

Process Control Block (PCB)

A data structure the OS maintains for every process, identified by an integer process ID (PID). It keeps all the information needed to track the process:
  • Process state – running, waiting, etc.
  • Program counter – location of the next instruction
  • CPU registers – contents of all process-centric registers
  • CPU-scheduling information – priorities, scheduling-queue pointers
  • Memory-management information – memory allocated to the process
  • Accounting information – CPU used, clock time elapsed, time limits
  • I/O status information – devices allocated, list of open files
The PCB layout depends completely on the OS. It is kept throughout the process’s lifetime and deleted once the process terminates.

3. Process Scheduling

Queues, scheduling times, and context switching.

The scheduler

The process scheduler selects among available processes for the next execution on a CPU core. Goal: maximize CPU use and switch processes onto the CPU core quickly. Processes migrate among the various queues.

Job queue

At the start, all processes are stored in the job queue.

Ready queue

Set of all processes residing in main (primary) memory, ready and waiting to execute.

Wait queues

Processes waiting for an event (e.g. I/O). When a running process needs I/O, the OS changes its state from running to waiting.

Times related to a process

  • Arrival time – when the process enters the ready queue
  • Completion time – when the process completes its execution
  • Turnaround time – total time from arrival to completion (completion − arrival)
  • Burst time – total CPU time required to execute the whole process, not including waiting time. It is hard to know before running, so scheduling based on burst time cannot be implemented exactly in reality
  • Waiting time – total time the process waits for the CPU (turnaround − burst)
  • Response time – difference between arrival and the time it first gets the CPU (first CPU − arrival)

Context switch

Switching the CPU to another process requires a state save of the current process and a state restore of a different one. The kernel saves the old context in its PCB and loads the saved context of the new process. Context-switch time is pure overhead: the system does no useful work while switching, and the time depends on hardware support.

    4. Operations on Processes

    Creating and terminating processes.

    Process creation

    Processes can execute concurrently and are created and deleted dynamically. A creating process is the parent; the new ones are its children. Children can create more processes, forming a tree of processes. Each process has a unique integer pid.
    • A child needs resources (CPU time, memory, files, I/O devices). It may get them directly from the OS or be limited to a subset of the parent’s resources. The parent may partition or share some resources among children.
    • Restricting children to a subset of the parent’s resources prevents any process from overloading the system by creating too many children.

    Two execution possibilities

    1. The parent continues concurrently with its children.
    2. The parent waits until some or all children terminate.

    Two address-space possibilities

    1. The child is a duplicate of the parent (same program and data).
    2. The child has a new program loaded into it.

    UNIX: fork(), exec(), wait()

    A new process is created by fork(). After it, one of the two processes typically calls exec() to replace its memory space with a new program (it loads a binary file and starts executing it). The parent can create more children or call wait() to move itself off the ready queue until the child terminates.
    Parent running→Child = copy→Child runs new program→Parent resumes
    1. The parent process is running.
    2. The parent calls fork(): a child is created as a duplicate (same program and data) with a new PID.
    3. The child calls exec(): its memory is replaced by a new program.
    4. The parent calls wait() and leaves the ready queue until the child ends.
    5. The child finishes and calls exit(); its resources are deallocated.
    6. The parent wakes up and continues.

    Process termination

    • A process terminates when it finishes its last statement and calls exit(). The OS deallocates and reclaims all resources: physical and virtual memory, open files, I/O buffers.
    • A process can terminate another via a system call (e.g. TerminateProcess() in Windows). The parent must know its children’s identities, so the new process’s identity is passed to the parent.
    • A parent may terminate a child if the child exceeded its resource usage, or if the parent is exiting and the OS does not allow children to continue.
    • Cascading termination: if a process terminates (normally or abnormally), all its children must also be terminated. Normally initiated by the OS.
    • A parent waits for a child using wait().
    • A zombie process has terminated, but its parent has not yet called wait().

    5. IPC: Shared Memory

    Interprocess communication (IPC) and the producer-consumer problem.

    Independent vs cooperating processes

    Processes can be independent or cooperating. A cooperating process can affect or be affected by other processes, including by sharing data (a reason: information sharing). Cooperating processes need IPC. Two models: shared memory and message passing.

    Shared-memory model

    • An area of memory shared among the communicating processes.
    • Communication is under the control of the user processes, not the OS.
    • Major issue: a mechanism that lets user processes synchronize their actions when accessing shared memory.

    Producer-consumer problem

    A paradigm for cooperating processes: a producer produces information consumed by a consumer. Two variations:

    Unbounded buffer

    No practical limit on buffer size. Producer never waits; consumer waits if there is nothing to consume.

    Bounded buffer

    Fixed buffer size. Producer must wait if all buffers are full; consumer waits if there is nothing to consume.

    6. IPC: Message Passing

    Communicating without sharing the same address space.

    Basics

    Message passing lets processes communicate and synchronize without sharing the same address space or shared variables. It is especially useful in a distributed environment (processes on different computers connected by a network), e.g. an Internet chat program.
    • Two operations: send(message) and receive(message). Message size is fixed or variable.
    • For P and Q to communicate they must establish a communication link and exchange messages via send/receive.

    1. Direct communication

    Processes name each other explicitly: send(P, message), receive(Q, message).
    • Links are established automatically
    • A link belongs to exactly one pair of processes
    • Exactly one link per pair
    • May be unidirectional, usually bi-directional

    2. Indirect communication

    Messages go to and from mailboxes (ports), each with a unique id. Processes communicate only if they share a mailbox.
    • A link may be associated with many processes
    • A pair may share several links
    • Unidirectional or bi-directional
    Operations: create a mailbox, send/receive through it, delete it. send(A, message), receive(A, message).

    Mailbox sharing problem

    P1, P2 and P3 share mailbox A. P1 sends; P2 and P3 receive. Who gets the message? Solutions: allow a link with at most two processes; allow only one process at a time to execute receive; or let the system select the receiver arbitrarily and notify the sender.

    3. Buffering

    A queue of messages attached to the link, implemented in three ways:
    • Zero capacity – no messages queued. Sender must wait for the receiver (rendezvous).
    • Bounded capacity – finite length of n messages. Sender must wait if the link is full.
    • Unbounded capacity – infinite length. Sender never waits.

    7. Chapter Summary

    Review this right before the exam.

    • Process = program in execution (active); program = passive file on disk. One program can be many processes.
    • Memory layout: text, data, heap, stack. Text/data fixed; heap and stack grow toward each other.
    • States: New, Ready, Running, Waiting, Terminated. The PCB (PID, state, PC, registers, scheduling, memory, accounting, I/O) is kept for each process.
    • Queues: job, ready (in main memory), wait. The scheduler maximizes CPU use.
    • Times: arrival, completion, turnaround, burst, waiting, response.
    • Context switch: save old state in its PCB, load new state. Pure overhead.
    • fork() creates, exec() replaces the program, wait() waits for a child, exit() terminates. Cascading termination; zombie = terminated but not yet waited for.
    • IPC: shared memory (user-controlled, needs synchronization; producer-consumer) vs message passing (send/receive; direct, indirect via mailboxes; zero/bounded/unbounded buffering).
