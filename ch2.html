1. Operating-System Services


What the OS offers to programs and users.


Big idea
Operating systems provide an environment for the execution of programs and services to programs and users. The services fall into two groups: those that help the user, and those that keep the system itself efficient.


A. Services that help the user




User interface
Almost all OSs have a UI. It varies between Command-Line (CLI), Graphical (GUI), touch-screen, and Batch.


Program execution
The system must load a program into memory, run it, and end execution either normally or abnormally (indicating an error).


I/O operations
A running program may need I/O, which may involve a file or an I/O device.


File-system manipulation
Programs need to read and write files and directories, create and delete them, search them, list file information, and manage permissions.


Communications
Processes exchange information on the same computer or over a network, via shared memory or message passing (packets moved by the OS).


Error detection
The OS must constantly watch for errors in the CPU and memory hardware, I/O devices, and user programs, and take the appropriate action for correct and consistent computing. Debugging facilities help users and programmers.




B. Services for efficient operation (resource sharing)




Resource allocation
With multiple users or jobs running concurrently, resources must be allocated to each: CPU cycles, main memory, file storage, I/O devices.


Logging
Keeps track of which users use how much, and what kinds, of computer resources.


Protection & security
Owners of information in multiuser or networked systems may want to control its use; concurrent processes should not interfere with each other.

2. User and OS Interface


Three common ways users talk to the OS. Some systems offer two or all three.




Command-line interface (CLI)
Also called the command interpreter. Users type commands directly. Linux, UNIX and Windows treat it as a special program that runs when a process starts or a user logs on.

When several interpreters exist they are called shells: on UNIX/Linux the C shell, Bourne-Again shell (bash), Korn shell, and others.


Graphical user interface (GUI)
A user-friendly desktop metaphor: mouse, keyboard and monitor. Icons represent files, programs and actions; mouse buttons over objects show information, options, run functions, or open a directory (folder).

Many systems include both CLI and GUI. Windows is a GUI with a CLI “command” shell (cmd).


Touch-screen interface
Touch devices need new interfaces where a mouse is not possible or not desired:
  • Actions and selection based on gestures
  • Virtual keyboard for text entry
  • Voice commands









3. System Calls


The doorway from programs into the kernel.


What is a system call?
System calls provide an interface to the services made available by an operating system. They are generally available as functions in C and C++; some low-level tasks (direct hardware access) may need assembly language.

Example: copy one file to another. The program first needs the file names. In UNIX: cp in.txt out.txt. Or in an interactive program it asks the user, which needs a sequence of system calls (write prompt, read keyboard, open files, read, write, close, exit).




API
Programmers rarely see system calls (systems execute thousands per second). They code to an Application Programming Interface (API), which specifies the functions available, their parameters, and the return values expected.

API functions invoke the real system calls. Example: Windows CreateProcess() calls the kernel’s NTCreateProcess().


Run-time environment (RTE)
Provides the system-call interface linking to the OS’s system calls. Each call has a number, and the interface keeps a table indexed by these numbers. It invokes the call in the kernel and returns the status and return values. The caller only needs to obey the API; details are hidden by the API and managed by the RTE (the run-time support library included with the compiler).




Interactive: what happens when you call printf()


Application→API / RTE (C library)→System-call table→Kernel


  1. The program calls printf("Hello"), an API / C-library function.
  2. The C library prepares the parameters and the system-call number for write().
  3. A trap enters kernel mode; the system-call interface looks up the number in its table.
  4. The kernel executes write() and the device does the output.
  5. Status and return values go back, the mode returns to user mode, and the program continues.




System-call parameter passing
Often more than the call’s identity is needed (type and amount vary by OS and call). Three general methods:



1. Registers
The simplest method. Problem: there may be more parameters than registers.
R1=fd R2=buf R3=n


2. Block / table
Parameters are stored in a block in memory; its address is passed in a register. Used by Linux and Solaris.
R1 → [x, y, z]


3. Stack
Parameters are pushed onto the stack by the program and popped off by the OS.
push z, y, x


The block and stack methods do not limit the number or length of parameters.







4. Types of System Calls


Six major categories. Tap to open each.


1. Process control
  • create process, terminate process
  • end, abort
  • load, execute
  • get / set process attributes
  • wait for time; wait event, signal event
  • allocate and free memory
  • dump memory if error; debugger (single-step execution)
  • locks for managing access to shared data


2. File management
  • create file, delete file
  • open, close file
  • read, write, reposition
  • get and set file attributes


3. Device management
  • request device, release device
  • read, write, reposition
  • get / set device attributes
  • logically attach or detach devices


4. Information maintenance
  • get / set time or date
  • get / set system data
  • get / set process, file, or device attributes


5. Communications
  • create, delete communication connection
  • send, receive messages
  • transfer status information
  • attach or detach remote devices


6. Protection
  • Control access to resources
  • get file permissions, set file permissions

Standard C library example
A C program calls the library function printf(), which in turn calls the write() system call. The library acts as the API layer on top of the kernel.







5. System Services


Programs that come with the OS versus programs users run.




Background services
  • Launched at boot time; some run for startup then terminate, others from boot to shutdown
  • Provide disk checking, process scheduling, error logging, printing
  • Run in user context, not kernel context
  • Known as services, subsystems, daemons


Application programs
  • Don’t pertain to the system
  • Run by users
  • Not typically considered part of the OS
  • Launched by command line, mouse click, or finger poke









6. Linkers and Loaders


How source code becomes a running program.


Interactive: from source code to running program


Source code→Object files→Linker→Executable→Loader → Memory


  1. The programmer writes the source code.
  2. The compiler/assembler produce relocatable object files, designed to be loaded at any physical memory location.
  3. The linker combines the object files (and brings in libraries) into a single binary executable file.
  4. The executable resides on secondary storage. Standard file formats let the OS know how to load and start it.
  5. The loader brings it into main memory. Relocation assigns final addresses and adjusts code and data to match. Then it runs.






Linker
An important utility that takes the object files (from the assembler and compiler) and other code and joins them into a single executable file. Its main function is to generate executable files.


Loader
A vital OS component responsible for loading programs and libraries into main memory. Its input is the executable file produced by the linker. It loads the executable code into memory so it can be executed.









7. Why Applications are OS-Specific


Why a Windows app does not simply run on Linux.


The reasons
  • Apps compiled on one system are usually not executable on other operating systems
  • Each OS provides its own unique system calls
  • Each OS has its own file formats, etc.


How an app can run on multiple OSs
  • Written in an interpreted language (Python, Ruby) with an interpreter available on many OSs
  • Written in a language that includes a virtual machine containing the running app (like Java)
  • Written in a standard language (like C) and compiled separately on each OS







8. Chapter Summary


Review this right before the exam.


    

  • OS services: user-helpful (UI, program execution, I/O, file system, communications, error detection) and efficiency (resource allocation, logging, protection and security).
    • 

  • Interfaces: CLI (shells), GUI (desktop metaphor, icons), touch-screen (gestures, virtual keyboard, voice).
    • 

  • System calls are the interface to OS services; programmers use an API, and the RTE maps calls to the kernel using a numbered table.
    • 

  • Parameters pass via registers, a memory block (Linux, Solaris), or the stack.
    • 

  • Six call types: process control, file management, device management, information maintenance, communications, protection.
    • 

  • Daemons run in user context; application programs are not part of the OS.
    • 

  • Compiler → object files → linker → executable → loader → memory; relocation assigns final addresses.
    • 

  • Apps are OS-specific because of unique system calls and file formats; interpreters, VMs, or recompiling make them portable.
