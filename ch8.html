1. System Model and Deadlock

What resources are, how threads use them, and what “deadlocked” means.

Resources

A system has a finite number of resources to be distributed among competing threads. Resources are partitioned into types (classes), each with some number of identical instances.
  • Examples of resource types: CPU cycles, files, I/O devices (network interfaces, DVD drives).
  • A system with four CPUs: the resource type CPU has four instances.
  • If a thread requests an instance of a type, any instance should satisfy it. If not, the instances are not identical and the classes were not defined properly.

Request – Use – Release

A thread must request a resource before using it and release it after. Normal sequence: 1. Request → 2. Use → 3. Release. The number requested may not exceed the total available: a thread can’t request two network interfaces if the system has only one. A system table records whether each resource is free or allocated.

Definition of deadlock

A set of threads is in a deadlocked state when every thread in the set is waiting for an event that can be caused only by another thread in the set. The events here are mainly resource acquisition and release.
In a deadlock, processes never finish executing, and system resources are tied up, preventing other jobs from starting.
Chapter objective: illustrate how deadlock can occur when mutex locks are used (for example two threads each holding one lock and waiting for the other’s).

2. The Four Necessary Conditions

A deadlock can arise only if all four hold simultaneously.

Mutual exclusion

At least one resource is held in a non-sharable mode: only one thread at a time can use it. A requesting thread must be delayed until it is released.

Hold and wait

A thread is holding at least one resource and waiting to acquire additional resources currently held by other threads.

No preemption

Resources cannot be preempted: a resource can be released only voluntarily by the thread holding it, after it has completed its task.

Circular wait

A set {T0, T1, …, Tn} of waiting threads exists such that T0 waits for a resource held by T1, T1 for T2, …, Tn−1 for Tn, and Tn for T0.

Interactive: break a condition

Tap a condition to switch it off. All four must be ON for a deadlock to be possible. This is the idea behind deadlock prevention.

3. Resource-Allocation Graph

A directed graph that describes deadlocks precisely.

The graph

A system resource-allocation graph has a set of vertices V and a set of edges E. V is split into P = {P1, …, Pn} (all active processes) and R = {R1, …, Rm} (all resource types).
  • Request edge Pi → Rj: Pi has requested an instance of Rj and is currently waiting for it.
  • Assignment edge Rj → Pi: an instance of Rj has been allocated to Pi.
  • Drawing: each process = circle; each resource type = rectangle, with one dot per instance.
  • When Pi requests an instance, a request edge is inserted. When it can be fulfilled, the request edge is instantly transformed into an assignment edge. When Pi releases the resource, the assignment edge is deleted.

Reading the slide example

P = {P1, P2, P3} · R = {R1, R2, R3, R4} · E = {P1→R1, P2→R3, R1→P2, R2→P2, R2→P1, R3→P3}
Instances: R1 ×1, R2 ×2, R3 ×1, R4 ×3.
  • P1 holds an instance of R2 and waits for R1.
  • P2 holds an instance of R1 and of R2 and waits for R3.
  • P3 holds an instance of R3.

Cycles and deadlock

  • No cycle → no process is deadlocked.
  • Cycle and every resource type has exactly one instance → deadlock has occurred (cycle is necessary and sufficient).
  • Cycle and resource types have several instances → maybe: a cycle is necessary but not sufficient.

4. Methods for Handling Deadlocks

Three general ways to deal with the problem.

Ignore it

Ignore the problem altogether and pretend that deadlocks never occur in the system.

Prevent or avoid

Use a protocol so the system never enters a deadlocked state: deadlock prevention or deadlock avoidance.

Detect and recover

Allow the system to enter a deadlocked state, detect it, and recover. The system provides an algorithm that examines the state to see whether a deadlock has occurred, and an algorithm to recover.

Deadlock prevention

A set of methods to ensure that at least one of the necessary conditions cannot hold.

Deadlock avoidance

The OS is given additional information in advance about which resources a process will request and use during its lifetime.

5. Deadlock Prevention

Make sure at least one of the four conditions can never hold. Tap to open each.

1. Mutual exclusion
The mutual exclusion condition must hold for some resources: at least one resource must be non-sharable. Sharable resources (such as read-only files) do not require mutually exclusive access and so cannot be involved in a deadlock. We usually cannot prevent deadlocks by denying this condition, because some resources are inherently non-sharable.
2. Hold and wait
Ensure a process never holds a resource while waiting for another:
  • Protocol 1: a process requests and is allocated all its resources before it begins execution.
  • Protocol 2: a process requests resources only when it has none. It may request some and use them; before requesting any additional ones, it must release all it currently holds.
3. No preemption
Protocol: if a process is holding some resources and requests another that cannot be immediately allocated (it must wait), then all the resources it currently holds are preempted. The process is restarted only when it can regain its old resources as well as the new ones it is requesting.
4. Circular wait
Impose a total ordering of all resource types and require that each process requests resources in an increasing order of enumeration. With this protocol a circular wait can never form.

Condition → how to prevent it

ConditionPrevention idea
Mutual exclusionUse sharable resources (they can’t cause deadlock)
Hold and waitRequest all resources first, or request only when holding none
No preemptionPreempt all held resources when a request must wait
Circular waitTotal ordering of resource types; request in increasing order

6. Deadlock Avoidance and the Banker’s Algorithm

Decide dynamically whether granting a request keeps the system safe.

Avoidance

Requires the OS to have a priori information about how each process will use resources. For every request, the system considers the resources currently available, the resources currently allocated to each process, and the future requests and releases of each process.
  • Simplest and most useful: each process declares the maximum number of resources of each type it may need.
  • The algorithm dynamically examines the resource-allocation state to ensure a circular-wait condition can never exist. The state is defined by the available and allocated resources and the maximum demands of the processes.

Safe state

A state is safe if the system can allocate resources to each process (up to its maximum) in some order and still avoid deadlock. Formally: a system is safe only if there exists a safe sequence.
SAFEsafe sequence exists
UNSAFEmay lead to deadlock
DEADLOCKalways unsafe
  • A safe state is not a deadlocked state; a deadlocked state is an unsafe state.
  • Not all unsafe states are deadlocks; an unsafe state may lead to a deadlock.
  • As long as the state is safe, the OS can avoid unsafe (and deadlocked) states.

Banker’s algorithm

Named because it could be used in a bank to ensure it never allocates its cash so that it can no longer satisfy all customers’ needs. A new process must declare the maximum instances of each resource type it may need. When a process requests resources, the system checks whether allocating them leaves the system in a safe state. If yes, they are allocated; otherwise the process must wait until others release enough.

Data structures (n processes, m resource types):

  • Available – vector of length m: Available[j] = k means k instances of Rj are available.
  • Max – n × m matrix: Max[i][j] = k means Pi may request at most k instances of Rj.
  • Allocation – n × m matrix: Allocation[i][j] = k means Pi currently holds k instances of Rj.
  • Need – n × m matrix of remaining needs: Need[i][j] = Max[i][j] − Allocation[i][j]
Vector comparison: X ≤ Y iff X[i] ≤ Y[i] for all i. Example: X = (1,7,3,2), Y = (0,3,2,1) → Y ≤ X.

Safety algorithm and resource-request algorithm

Safety: Work = Available; Finish[i] = false. Find a process i with Finish[i] = false and Need[i] ≤ Work; then Work = Work + Allocation[i] and Finish[i] = true. Repeat. If all Finish are true → safe (the order found is a safe sequence).
Request (Requesti): (1) if Request ≤ Need, continue, else error (exceeded maximum claim). (2) If Request ≤ Available, continue, else Pi must wait. (3) Pretend to allocate: Available −= Request, Allocation += Request, Need −= Request, then run the safety algorithm: safe → grant; unsafe → Pi waits and the old state is restored.

7. Chapter Summary

Review this right before the exam.

  • Deadlock = every thread in a set waits for an event only another thread in the set can cause. Threads use resources by request → use → release.
  • Four necessary conditions (all must hold): mutual exclusion, hold and wait, no preemption, circular wait.
  • Resource-allocation graph: request edge Pi→Rj, assignment edge Rj→Pi. No cycle = no deadlock; cycle + single instances = deadlock; cycle + multiple instances = maybe.
  • Handling: ignore, prevent/avoid, or detect and recover.
  • Prevention breaks one condition: sharable resources; request all first / release before requesting; preempt held resources; total ordering of resources.
  • Avoidance needs max claims in advance; keeps the system in a safe state (a safe sequence exists). Deadlock ⊂ unsafe; unsafe ≠ always deadlock.
  • Banker’s algorithm: Available, Max, Allocation, Need = Max − Allocation. Grant a request only if it leaves the system safe.
